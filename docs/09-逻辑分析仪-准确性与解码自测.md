# 逻辑分析仪：采集口径、准确性与解码自测

> 这份文档是**确定性记录**：改采集链路或解码器之前先看这里，改完按第 5 节的清单回归。
> 目的不是把 KDock 变成计量仪器，而是保证"同一份采样，今天和以后解出来的东西一样"。

## 1. 边界：我们负责什么，不负责什么

| 环节 | 谁负责 | KDock 做什么 |
| --- | --- | --- |
| 采样时钟 / 模拟前端 | **设备厂商**（晶振、比较器） | 原样接收，不重采样、不加时间戳、不做修正 |
| USB 协议 / 固件上传 | **sigrok**（`fx2lafw` / `dreamsourcelab-dslogic` / `saleae-logic16`） | 调 `sigrok-cli`，解析它给的原始采样 |
| 采样 → 通道位 | KDock | 按 libsigrok 的 `unitsize` 解包（见第 2 节） |
| 波形 / 测量 / 解码 | KDock（`src/logic-decoders.js`） | 19 个自研解码器 |

**结论**：时间轴精度 = 设备规格（FX2LP 典型 ±30~50 ppm）。KDock **不做精度标定**，只做功能自测
（点数对不对、已知信号能不能解出来）。

## 2. 采样数据的字节口径（最容易踩的坑）

`sigrok-cli ... -O binary` 写的是 libsigrok 的 `logic->data`，**每个采样占几个字节由驱动的
`unitsize` 决定，不是由"这次选了几个通道"决定**：

| 驱动 | unitsize | 依据 |
| --- | --- | --- |
| `fx2lafw`（8 通道，如初代 Saleae Logic） | **1 字节/采样** | `fx2lafw/protocol.c`：`unitsize = sample_wide ? 2 : 1` |
| `fx2lafw`（16 通道，如 sigrok-fx2-16ch） | **2 字节/采样** | 同上（`sample_wide = true`） |
| `dreamsourcelab-dslogic` | **恒为 2 字节/采样** | `protocol.c`：`send_data()` 里 `.unitsize = sizeof(uint16_t)` |
| `saleae-logic16` | **恒为 2 字节/采样** | `protocol.c`：`logic.unitsize = 2` |

位序：**bit0 = 本次 `-C` 列表里的第一个通道**；16 通道时低字节 = 通道 0–7，高字节 = 通道 8–15
（小端）。KDock 的 `logics.rs` 先按"设备总通道数 > 8 → 2 字节"猜，再用**实际文件长度**兜底，
`bytes.len() % bps != 0` 就换另一个 unitsize 或直接报错 —— 绝不做"看起来差不多"的猜测。

## 3. 当前已验证的硬件

| 设备 | 驱动 | 状态 | 验证内容 |
| --- | --- | --- | --- |
| Saleae Logic（初代，8ch，VID:PID 0925:3881） | `fx2lafw` | ✅ 真机验证 | 1 MHz × 200k（0.54 s）、24 MHz × 1M（0.68 s）、点数与时长一致、SVG 波形 8 路、测量/解码管线贯通 |
| DreamSourceLab DSLogic（Basic/Plus/Pro/U2/U3） | `dreamsourcelab-dslogic` | ⚠️ 固件已装、**待真机验证** | 9 个固件/位流按 sigrok wiki 对照表从 DSView 官方仓库下载并 MD5 校验；代码路径与 fx2lafw 相同 |

已知限制：
- 这台 Saleae Logic 报 20 kHz–48 MHz，但 **48 MHz 实测只拿到几千点**（设备限制）。界面按设备上报的
  列表给，实际点数不足会明确提示（"设备只采到 X / Y 点"）。
- 连续采集中如果设备被其它进程占用，sigrok 返回 `LIBUSB_ERROR_ACCESS`；界面会提示"设备被占用 /
  重新插拔"，或对设备做一次 PnP 重启（`pnputil /restart-device`）。
- 单次采集上限 2000 万点（前端要按通道展开成 `Uint8Array`，再大就吃内存）。

## 4. 解码器的现状（重要）

19 个解码器**目前只用内置示例场景验证过**。示例场景是按协议规范手工拼出的**理想波形**，
所以：

- ✅ 能证明：位解析 / 字段顺序 / 校验算法 / 输出排版 是对的；
- ❌ 不能证明：真实设备的抖动、毛刺、时钟拉伸、总线冲突、错误帧处理。

**因此解码器状态统一记为「示例验证（demo-verified）」，不写成「真机验证」**。真机验证按第 5 节做一次即可
（解码器与设备无关，不需要每台设备重测）。

## 5. 回归清单（改完必须跑）

### 5.1 采集链路（任何 `logic.rs` / `logic-analyzer.js` 改动）

1. `sigrok-cli --scan` 能列出设备（8ch / 16ch 各一次）。
2. 8 通道：1 MHz × 200000 点 → 文件长度 = 200000 字节，界面显示 `8 ch / 200000 samples / 200 ms`。
3. 16 通道：任意采样率 × 1000 点 → 文件长度 = 2000 字节，界面 16 路都能单独翻转（用已知信号）。
4. 故意请求 48 MHz × 1M（这台老 Saleae）→ 必须出现"只采到 X / Y 点"提示，而不是静默截断。

### 5.2 解码器（任何 `logic-decoders.js` 改动）

用**已知发送端**（F4 / ESP32 发固定帧）采一次，逐条比对：

| 协议 | 已知信号 | 期望 |
| --- | --- | --- |
| UART | 115200 8N1 发 `AA 55 01 02 03` | 5 字节，值一致，无 framing error |
| SPI | mode 0 / 3，1 MHz，发 `9F 00 00 00` | 4 字节 + JEDEC ID |
| I2C | 100k / 400k，写 `0x50` 寄存器 | 地址 + 数据 + ACK |
| CAN | 250k / 500k 标准帧 | ID / DLC / 数据一致 |

交叉验证：同一份采集存成 VCD，用 PulseView + sigrok 解码器再解一遍，结果必须一致。
