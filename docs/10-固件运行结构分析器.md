# 固件运行结构分析器：全固件函数、调用链与 CFG

> 适用版本：KDock `0.3.x` 开发版 / 便携测试版
> 分析后端：`pybingraph 0.2.5` + `angr 10.0.4` + Python 3.13.13
> 本文描述当前实际行为；“全固件函数”模式不做 `main` 可达性裁剪。

## 1. 功能定位

“运行结构”页把 ELF、PE、AXF、OUT 或裸机 BIN 载入 angr，先恢复函数与调用图，
再在 KDock 自己的画布上做分层布局、过滤和交互。它不是反编译器的替代品，重点解决
三个工程问题：

1. **完整看清固件**：全固件模式列出分析器识别出的每个函数，而不是只列 `main`
   可达的一小部分；
2. **知道程序怎么跑**：main 运行链按真实调用顺序展开，中断处理函数从向量表单独挂载；
3. **在超大图上仍能操作**：库函数默认汇总、重复调用边合并、按层自动整理，选中函数
   后再按需查看基本块。

页面数据全部来自本机分析器，不把固件上传到网络，也不依赖浏览器 `localStorage`
分组。KDock 只保存“上次选择的固件路径”和页面偏好。

## 2. 架构与数据流

```text
┌──────────────────────────────────────────────────────────────┐
│ KDock WebView                                                │
│  src/runtime-graph.js                                        │
│  画布 / 分层布局 / 库汇总 / 搜索 / 选中详情 / CFG             │
└───────────────┬──────────────────────────────────────────────┘
                │ invoke("runtime_analyze", ...)
┌───────────────▼──────────────────────────────────────────────┐
│ Rust: src-tauri/src/runtime_graph.rs                         │
│ 便携 Python 定位 / 随机端口 / 子进程生命周期 / HTTP 超时      │
└───────────────┬──────────────────────────────────────────────┘
                │ http://127.0.0.1:<random>/api/...
┌───────────────▼──────────────────────────────────────────────┐
│ Python 子进程（独立进程，不嵌入 WebView）                     │
│  run.py -> launcher -> pybingraph -> angr CFGFast             │
│  /api/functions/json  全固件函数与调用边                       │
│  /api/runtime/json    main 运行链、中断、调用点、基本块         │
└──────────────────────────────────────────────────────────────┘
```

### 2.1 进程与端口

- 分析器只绑定 `127.0.0.1`，不监听局域网；
- KDock 每次启动分析器时向系统申请一个空闲端口，不写死 `19003`；
- 分析器以子进程运行，KDock 退出时回收整棵进程树；
- 连续分析同一份固件且加载参数不变时复用已运行的分析器；切换 ELF/BIN 或 BIN
  基址/入口/向量表时才重启；
- 启动等待上限 45 秒，单次分析 HTTP 超时 180 秒。首次加载 angr 和扫描大固件可能
  接近这个上限，后续请求通常明显更快。

### 2.2 Rust 与 Python 的职责边界

Rust 负责安全边界和进程编排，不解析 ELF：

- 检查分析器是否随包存在；
- 启动、探测、停止 Python；
- 把固件相对路径和 BIN 参数转成分析器环境；
- 读取 HTTP JSON，并附加实际端口和根目录；
- 处理超时、非 2xx 响应和 chunked 响应体。

Python 负责二进制分析：

- 加载 ELF/PE/BIN；
- 运行 `CFGFast`，得到函数、基本块与调用边；
- 解析 Cortex-M 向量表，识别中断 Handler；
- 返回全固件函数表或 main 运行结构 JSON。

## 4. 为什么不需要用户安装 Python、uv 或 Graphviz

### 4.1 Python 版本

angr 和 pybingraph 的依赖矩阵对 Python 版本敏感。用户机器上可能是 Python 3.6、
3.11、3.14，甚至完全没有 Python；如果让 KDock 调用系统 Python，就会出现：

- `pip` 命令不存在；
- 32 位 Python 无法加载 x64 二进制依赖；
- 系统已装新版/旧版包，版本冲突；
- PATH 指向另一套解释器；
- `uv` 未安装，无法解析锁定环境。

因此 KDock 携带**独立 Python 3.13.13**，不读系统 `PYTHONPATH`，只使用自己的
`site-packages`。用户装不装 Python、装几个版本，都不影响运行结构。

### 4.2 uv

`uv` 只用于维护和 CI 构建，不是运行依赖。构建脚本顺序为：

1. 有 `uv`：用 `uv pip install --python <嵌入式 Python>` 安装锁定依赖；
2. 没有 `uv`：下载 Python 官方 `get-pip.py`，用它给嵌入式 Python 引导 pip；
3. 再按 `requirements.txt` 安装同样版本。

所以 CI 不需要预装 `uv`，最终用户更不需要。

### 4.3 Graphviz

运行结构页面使用 KDock 原生 DOM/SVG 画布；`/api/functions/json` 与
`/api/runtime/json` 只返回数据，不调用 `dot`。Graphviz 即使存在也只用于旧的
上游 SVG 页面。默认构建用 `-NoGraphviz`，不把它放进便携包。

## 5. 分析范围与单条链路

### 5.1 全固件函数（默认）

接口：`/api/functions/json?filepath=<相对路径>`

- 收集 `CFGFast` 调用图里的所有节点；
- 包括 `main` 不可达的初始化代码、驱动、库函数和孤立函数；
- 每个节点带地址、名称、大小、基本块数和块地址；
- 每条调用边带源、目标以及后续可解析的调用次数；
- 对 ELF 可执行段按符号完整范围补扫 `BL/BLX`，修复 CFGFast 提前截断函数、
  导致循环体调用丢失的问题；
- 不推断 `mainReachable`，因此 UI 统一显示中性的“函数/FUNC”；
- 默认“入口骨架”只改变**画面表示**，不会从数据里删除函数；展开节点或关闭骨架
  即可查看完整调用图；
- 库函数和自定义分组默认收起下游分支，节点仍保留在原调用位置。

这是“为什么函数少了”问题的最终答案：默认不再请求运行链接口，而是请求全固件接口。
实测同一份 `hpf416serial.elf` 有：

```text
全固件函数：1301
全固件调用边：9086
无入边根函数：265
```

运行链（779 个 main 可达函数）只是全固件的一个子集，不能用它判断固件
到底有多少函数。

### 5.2 main 运行链

接口：`/api/runtime/json?filepath=<相对路径>`

- 以 `main` 为唯一根；
- 用调用图求 `main` 的全部后代；
- 按真实 `BL/BLX/CALL` 指令地址排序调用点；
- 返回 main 可达集合，供 UI 在“只看 main”时过滤。

同一份固件实测：

```text
main 可达：779
中断 Handler：18
中断作用域可达：64
中断专属：57
运行结构原始节点：833
运行结构调用边：7540
```

UI 默认用入口骨架只展开 main 的主工作分支，其余分支按需展开，所以画布可读性高于
“全固件 1301 个原始函数”。

### 5.3 单条链路分析

当全固件图太大时，不要盯着整张图找关系。先在任意模式下选中一个函数，再点右侧
“拉这条链路”或顶部“用选中函数拉链路”：

| 选项 | 用途 |
| --- | --- |
| 向下调用 | 只看这个函数调用了谁，适合追协议处理、业务入口 |
| 向上调用者 | 只看谁调用了它，适合追回调、HAL 底层、库函数入口 |
| 双向 | 同时保留上下游，适合判断一个函数在系统中的位置 |
| 深度 1/2/3/5/8/全部 | 从根函数向外扩展的层数，默认 3 层 |

链路模式是在已获取的全固件调用图上本地裁剪，不需要重新运行 angr。根节点会加粗
高亮，右上角显示根函数名和地址。启用“入口骨架”时，全固件首屏只显示 main、main
的一级调用和其他弱连通组件入口；点击节点上的 `+`、双击节点或使用右侧“展开下游”
可以逐层展开，避免一次铺开上千个函数。

需要分析多个入口时，可以按住 `Ctrl` 或 `Shift` 点击多个函数，再使用
“拉选中链路”。例如同时选择 `fsm_init` 和 `XC7K160T_FSM`，方向选“向下”、深度
选“全部”，画布只保留两个根可达的逻辑树；其他函数不会进入当前链路视图。
链路视图使用紧凑函数卡和层级泳道：`L0` 为根，`L+1/L+2` 为下游，`L-1/L-2`
为上游；同层固定同列，跨级跳线以虚线弱化，生成后自动缩放到完整链路。
`main 运行链`和“全固件函数”在“展开全部”状态下也复用这套层级列布局；节点过多
的层会在同一泳道内拆成多个子列，避免单根超长列把应用函数和状态机压得不可见。
大图的连线会按样式和方向合并成少量 SVG 路径；选中模式下未选中节点时不绘制全量边，
拖动节点时按动画帧合并重绘，以降低 WebView2/GPU 在数千条调用线上的重绘压力。

全固件模式默认使用“入口骨架”和“连线 → 选中上下游”。选中函数后，橙色表示完整
上游路径，绿色表示完整下游路径；其余元素淡化。点击画布空白或按 `Esc` 可清除选中
状态和高亮。需要查看完整关系时点“展开全部”，或关闭“入口骨架”后手动展开分支。

### 5.4 中断作用域

中断不是 `main` 的普通分支。Python 端按以下顺序寻找 Cortex-M 向量表：

1. `BINGRAPH_NATIVE_VECTOR_BASE` 显式覆盖；
2. ELF/PE 的 `.isr_vector` 段；
3. `g_pfnVectors`、`__Vectors`、`_vectors`、`vector_table` 等符号；
4. 镜像最小地址（最后回退）。

从向量表第 1 项开始读 4 字节地址，只接受满足以下条件的函数：

- 地址存在于 `CFGFast` 函数表；
- 名称以 `_Handler` 或 `_IRQHandler` 结尾；
- 排除 `Reset_Handler`；
- 去重。

中断作用域是“从任一 Handler 可达”的所有函数。它与 main 集合可以重叠；共享
helper 不会被复制成多个节点。UI 中用橙色和 `IRQ` 标记，和全固件的蓝色中性函数
区分。

## 6. ELF / AXF / OUT 使用步骤

1. 打开左侧“运行结构”；
2. 点“选择 ELF / BIN…”，选择带符号的 `.elf`（`.axf`、`.out` 也可尝试）；
3. 范围保持“全固件函数”；
4. 点“分析运行结构”；
5. 首次分析等待 angr 加载和 `CFGFast`，状态栏会显示耗时；
6. 用“整理”按调用深度重新分层，或用“适应”缩放到当前画布；
7. 在搜索框输入函数名或地址定位；
8. 点击函数查看大小、基本块、调用点，需要时点“展开 CFG”。

带调试信息的 ELF 函数名最完整。Release 固件若被 strip，会得到 `sub_xxxx` 名称，
但全固件函数数量仍以分析器识别结果为准，不会因为无符号而人为删掉。

## 7. 裸机 BIN 使用步骤与限制

BIN 没有 ELF 头、段表和符号表，必须告诉分析器如何加载：

| 字段 | 必需性 | 示例 | 说明 |
| --- | --- | --- | --- |
| 加载基址 | 必需 | `0x08020400` | 文件第一个字节在地址空间中的位置 |
| 架构 | 必需 | `ARMCortexM` | angr 的 blob 架构；也支持其他 angr 架构名 |
| 入口 | 建议 | `0x0803c8a1` | 不给时由分析器从基址推导，ELF 符号缺失时可能需要手填 |
| 向量表基址 | 可选 | `0x08020400` | 不给时自动发现；裸机常与加载基址相同 |

参数从 KDock 右侧“BIN 参数”传入，Rust 会构造：

```text
文件名:基址:架构[:入口]
```

并通过 `BINGRAPH_NATIVE_BLOB_SPECS` 交给 Python。向量表基址通过
`BINGRAPH_NATIVE_VECTOR_BASE` 传入。

重要限制：

- BIN 中没有 `main` 符号，`main 运行链`模式无法可靠自动定位；全固件函数模式仍可用；
- 中断识别依赖向量表地址正确，且 Handler 名称通常无法从无符号 BIN 恢复；
- Thumb 函数地址的最低位是 1，但 angr/CFG 显示时可能按实际地址归一化，输入示例
  常写作 `0x08000101`；
- 基址填错不会报“格式错误”，而是得到错误地址、空调用图或大量 `sub_xxxx`；
- 优先使用 ELF。只有在无法获得 ELF 时才用 BIN，并保留 `.map` / 链接脚本作为人工
  核对依据。

实测样例：`runtime-smoke.bin` 由 `hpf416serial.elf` 用 `arm-none-eabi-objcopy -O binary`
生成，基址 `0x08020400`、入口 `0x0803c8a1`、向量表 `0x08020400` 时，指定入口可达
174 个函数。

## 8. 自动整理、筛选与信息密度

### 8.1 自动整理

- 每次分析后自动执行分层布局；
- 默认按调用深度从左到右，同层节点纵向排开；
- 先按弱连通分量拆分调用树，再在分量内部按调用深度和父节点重心排序；
- 小分量采用货架式打包，避免几十个独立入口排成一条超长竖列；
- 手动拖动后位置写入内存位置缓存，整理时优先复用；
- 画布支持滚轮缩放、拖动画布和拖动节点；
- 选择函数后点“拉这条链路”，在完整调用图上按方向和深度裁出单条链路；
- 选中时高亮完整上下游路径；点击空白或按 `Esc` 清除。

### 8.2 库函数汇总

内置规则覆盖：

- HAL / LL / CMSIS / SystemInit；
- `mem*`、`str*`、`printf/snprintf` 等 C 库；
- newlib、`__libc`、`__aeabi` 等运行时符号。

“折叠库函数”勾选时收起匹配函数的下游分支，取消勾选立即展开。分组支持名称前缀、
名称包含、正则、精确名称列表和地址范围；启用的分组会默认收起匹配分支。分组配置
保存在本机。节点仍保留在原调用位置，不会把所有库函数合并成一个 LIB 汇总节点。

### 8.3 调用边合并

同一调用者到同一目标可能有多条 `BL/BLX`。画布只画一条边，并在 `title` 和详情
中保留调用次数；这能显著减少全固件大图中的重复曲线，但不改变单函数详情里的
完整调用点列表。

### 8.4 作用域着色

| 作用域 | 颜色 / 标记 | 含义 |
| --- | --- | --- |
| 全固件函数 | 蓝色 `FUNC` | 普通函数，不表示 main 可达 |
| main 运行链 | 绿色 `main` | 从 main 可达 |
| 中断作用域 | 橙色 `IRQ` | 从向量表 Handler 可达 |

全固件接口的 `mainReachable` 字段为 `false` 只表示“此接口不做可达性判断”，
不表示该函数一定不可达。UI 已专门处理，不会把全固件函数全部标成中断。

## 10. 安全边界

- 分析器只监听 `127.0.0.1`；
- 端口由系统动态分配；
- Python 子进程以当前用户权限运行，不提权；
- 固件路径先由 KDock 解析为 `root` 下的相对路径，Python 再调用
  `resolve_under_root`，拒绝越界路径；
- 不上传固件、不访问外部服务；
- HTTP 请求只用于本机回环，响应大小和超时受 Rust 侧控制；
- KDock 退出或强制结束时回收子进程树，不残留占用目录的 `python.exe`；
- 分析器是独立进程，安全边界不同于 WebView 内的前端代码。

仍需注意：固件解析属于不可信输入处理。angr/pybingraph 是第三方分析器，不能保证
对恶意构造文件绝对安全。不要用它分析来源不明的固件；建议在受限账户或隔离机器
中处理敏感样本。

## 11. 常见问题

### Q1：提示“分析器未安装 / 去环境配置准备”

正式包先确认 `resources\bingraph\python\python.exe` 和 `run.py` 是否存在。若缺失，
在环境配置页点“准备 / 更新分析器”。开发包没有打包分析器时，开发构建会按上面的
路径寻找 `build-portable.ps1`。

### Q2：首次分析很慢

首次启动要初始化 angr、加载依赖并运行 `CFGFast`，几十秒正常。状态栏显示“分析中”
并保留日志。第二次请求同一固件通常更快；切换固件或 BIN 参数会重启分析器。

### Q3：函数数量比预期少

先确认范围是“全固件函数”，不是“main 运行链”。全固件默认启用“入口骨架”，统计
显示“当前可见 / 总数”；点“展开全部”可查看完整图。如果 ELF 被 strip，名称会变成
`sub_xxxx`，但总数仍按 CFGFast 识别结果计算。

### Q4：BIN 找不到 main

这是数据限制，不是 KDock 故障。BIN 没有符号表，无法可靠识别 `main`。请改用 ELF，
或在全固件模式按地址和调用关系分析；不要把 BIN 基址当成长度或文件偏移。

### Q5：中断列表为空

可能原因：

- 向量表不在自动发现的位置，需填“向量表”；
- 固件不是 Cortex-M 或向量表格式不同；
- Handler 名称不以 `_Handler` / `_IRQHandler` 结尾；
- 分析器未识别出 Handler 函数。

### Q6：全固件图太大 / 看不清

保持“入口骨架”，使用搜索框定位函数，或用节点 `+/-` 逐层展开。需要一次查看完整图
时点“展开全部”，再用“适应”缩放。全固件不会在首屏铺开上千个节点。

### Q7：Graphviz 没装能看吗？

能。KDock 的运行结构页只使用 JSON 和原生画布，不需要 Graphviz。旧的上游
`/callgraph` SVG 页面才可能需要 `dot`。

### Q8：分析结果和 `nm` 数量不一致

`nm` 只统计符号表；CFGFast 会额外识别无符号函数，也可能把跳转 stub、PLT 或
数据边界识别成函数。两者口径不同。KDock 全固件视图展示的是 angr 的分析结果，
不是简单的 `nm` 行数。

BIN 没有符号表和可靠的 `main` 名称，因此入口显示 `_start` 且中断识别通常为空；
函数数量和调用边也可能低于同源 ELF。这不是 KDock 少画了节点，而是输入格式能
提供的信息不同。需要 main/中断语义时优先分析 ELF。

检查命令：

```powershell
node --check src/runtime-graph.js
node --check src/main.js
cargo check --manifest-path src-tauri/Cargo.toml --locked

```

在不打开 GUI 时也可直接请求分析器：

```powershell
$base = "http://127.0.0.1:19003"
Invoke-RestMethod "$base/api/functions/json?filepath=hpf416serial.elf" |
  Select-Object totalFunctions,totalCalls,rootsTotal
```

具体数字随固件、编译器优化和 angr 版本变化，不应写死为产品断言。

## 13. 版本与升级注意事项

- Python 固定为 `3.13.x`，`pyproject.toml` 的 `requires-python` 是 `>=3.13,<3.14`；
- angr、pybingraph 和二进制 wheel 必须同时升级，不能只升级其中一个；
- 升级后重新生成 `uv.lock`、`requirements.txt` 和第三方许可清单；
- 系统 Python 3.14 不能直接复用这套 `site-packages`；
- 32 位 Windows 不在支持范围，便携 Python 与原生 wheel 都是 x64；
- 分析大固件时为临时构建环境和便携运行目录预留足够磁盘空间。

## 14. 维护约定

- 修改 `callgraph.py` 后必须同步 `resources/bingraph/launcher/bingraph_native/callgraph.py`
  并重新构建便携包；
- 升级 `pybingraph` / `angr` 时更新 `pyproject.toml`、`uv.lock`、`requirements.txt`，
  重新生成第三方许可清单；
- 不得把 `mainReachable=false` 直接解释成“中断”；全固件和运行链是两个数据模型；
- 不得默认依赖系统 Python、`uv`、Graphviz 或固定端口；
- 发布包必须带 `LICENSE`、`NOTICE`、`THIRD_PARTY_NOTICES.md` 和 `licenses/`；
- 大固件接口不要把每个基本块的完整指令文本塞进全量 JSON，按函数查询详情更稳。
