# 算法说明：视频带宽计算（Video Bandwidth）

> 本文档描述一套完整的"视频带宽计算 + 接口兼容性判定"算法。
> 算法与数据表来自公开标准：VESA CVT / DMT、CTA-861、DisplayPort 1.4 / 2.1、
> HDMI 2.0 / 2.1 / 2.2、VESA DSC；实现后用独立参考结果做过逐项对齐。

## 0. 这套算法在算什么

一句话：**给定一个"画面规格"（分辨率 / 刷新率 / 色深 / 色度格式），先算出它要吃掉多少链路带宽，
再逐条比对各种视频接口的各个版本能不能扛住。**

它不做物理层仿真，只做**带宽账**：

```text
需求带宽 ≤ 接口有效带宽                                  → Supported
需求带宽 > 接口有效带宽，但接口支持 DSC 且最低档位也够    → Supported, requires (light|heavy) DSC
其余                                                     → Not supported
```

因此页面上的 "Supported" 只代表**带宽够**，不代表"插上一定能点亮"（还要看 EDID、链路训练、线缆质量、
DSC 切片结构等，这些都不在模型内，见 §6.3）。

## 1. 输入与输出

### 1.1 输入

| 输入 | 取值范围 | 说明 |
| --- | --- | --- |
| `width` | 任意数 | 水平有效像素 |
| `height` | 任意数 | 垂直有效像素 |
| `refreshRate` | 任意数（Hz） | 垂直刷新率，可含小数 |
| `colorDepth` | `{6, 8, 10, 12, 14, 16}`（UI 可选） | **每通道**位数 |
| `colorFormat` | 见 §1.3 | 色度编码格式 |
| `timing` | `cvt` / `cvt_rb` / `cvt_rb2` / `dmt` / `cea` | 时序来源 |

> 注意：算法层对 `width` / `height` / `refreshRate` / `colorDepth` 的合法值域检查**非常宽松**，
> 只有 `NaN` 和 `0` 会被拒绝，负数、小数、超大值都会照算。详见 §6.4。

### 1.2 输出

| 字段（页面标签） | 定义 | 是否含消隐 |
| --- | --- | --- |
| `maximum`（Bandwidth） | 峰值带宽 = 像素时钟 × 色深 × `factor` | 含 |
| `line`（Line） | 行带宽 = 峰值 × `h_active / h_total` | 部分 |
| `active`（Active） | 有效画面带宽 = 实际刷新率 × 色深 × `h_active` × `v_active` × `factor` | 不含 |
| `dsc`（DSC） | DSC 理论下限 = 8 bpp × 像素时钟 | 含 |
| `clock` | 像素时钟（Hz） | — |
| `raw` | 完整时序明细（`htotal` / `vtotal` / 前后肩 / 极性 / `vic` / `dmt_id` …） | — |

单位统一 Gbps，显示时 `value / 1e9` 保留两位小数。任何一步失败则整体为 `N/A`（见 §6.5）。

### 1.3 色度格式与 `factor`

| `id` | 名称 | `factor` | 含义 |
| --- | --- | ---: | --- |
| `rgb444` | RGB 4:4:4 | 3 | 每像素 3 个分量 |
| `yuv444` | YUV 4:4:4 | 3 | 同上，亮度 / 色度分离 |
| `yuv422` | YUV 4:2:2 | 2 | 色度水平减半 |
| `yuv420` | YUV 4:2:0 | 1.5 | 色度水平 + 垂直减半 |

`factor` 就是"每像素的样本数"，公式里只出现这一个系数，**算法不区分 RGB 4:4:4 与 YUV 4:4:4**。

## 2. 总流程

```text
compute(width, height, refreshRate, colorDepth, factor, timing):
    ① 输入校验                     # 抛异常，见 §6.1
       width  = guardNumber(width,  "width")
       height = guardNumber(height, "height")
       refreshRate = guardNumber(refreshRate, "refreshRate")
       colorDepth  = guardNumber(colorDepth,  "colorDepth")

    ② 时序生成                     # 三条路径，见 §3
       if timing == "dmt":  T = lookupDMT(width, height, refreshRate)
       elif timing == "cea": T = lookupCEA(width, height, refreshRate)
       else:                 T = generateCVT(timing, width, height, refreshRate)

    ③ 派生带宽                     # 见 §4
       maximum = T.pixelClock × colorDepth × factor
       line    = maximum × T.h_active / T.h_total
       active  = T.refreshReal × colorDepth × T.h_active × T.v_active × factor
       dsc     = 8 × T.pixelClock

    ④ 逐接口判定                    # 见 §5.3
       for iface in [DP×5, USB-C Alt×2, HDMI×6]:
           verdict(iface, {maximum, dsc, clock, colorFormat, colorDepth})
```

## 3. 时序生成

时序部分有 **三条路径**：`cvt` / `cvt_rb` / `cvt_rb2` 走**公式生成**，`dmt` / `cea` 走**查表**
（但 DMT 命中 `cvt` / `cvt-rb` 类型的行时会转回公式生成，见 §3.4）。

### 3.1 三条 CVT 路径的公共前置

```text
CELL_GRAN = 8
h_active  = floor(width / 8) × 8      # ★ 宽度先向下取整到 8 的倍数：1366 → 1360
v_active  = height
aspect    = 由 h_active / v_active 反查（见下表）
```

**宽高比反查**：把 `v_active` 按 8 的步进分别套到 8 个候选比例上，取第一个等于 `h_active` 的：

```text
for k in [4/3, 16/9, 16/10, 5/4, 15/9, 43/18, 64/27, 12/5]:
    if 8 × round(k × v_active / 8) == h_active: aspect = k; break
else: aspect = "Unknown"
```

**`V_SYNC` 由宽高比决定**（`cvt` 与 `cvt_rb` 用，`cvt_rb2` 固定 8）：

| 宽高比 | 4:3 | 16:9 | 16:10 | 5:4 | 15:9 | 其它（含 Unknown） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `V_SYNC`（行） | 4 | 5 | 6 | 7 | 7 | 10 |

**三条路径的常量**：

| 常量 | `cvt` | `cvt_rb` | `cvt_rb2` | 含义 |
| --- | ---: | ---: | ---: | --- |
| `MIN_VSYNC_BP` | 550 µs | 460 µs | 460 µs | 垂直同步 + 后肩的最小时间预算 |
| `H_BLANK` 固定值 | — | 160 px | 80 px | 行消隐宽度 |
| 像素时钟量化步长 | 0.25 MHz | 0.25 MHz | 0.001 MHz | 像素时钟向下取整粒度 |
| `MIN_V_PORCH_RND` | 6 | 6 | 6 | 垂直前肩的最小值 |
| `V_SYNC` | 按宽高比 | 按宽高比 | 固定 8 | — |
| 行同步 / 前肩 / 后肩 | 公式推 | 32 / 48 / 80 | 32 / 8 / 40 | 单位 px |

> `cvt_rb2` 的像素时钟量化到 1 kHz（`0.001 MHz`），比另外两条精细 250 倍。

### 3.2 完整 CVT（`cvt`）

```text
H_PERIOD_EST (µs) = (1e6 / refreshRate − 550) / (v_active + 3)

V_SYNC_BP = floor(550 / H_PERIOD_EST) + 1
if V_SYNC_BP < V_SYNC + 6:  V_SYNC_BP = V_SYNC + 6

v_total = v_active + V_SYNC_BP + 3              # 末尾的 3 是垂直前肩

M = 30 − 0.3 × H_PERIOD_EST                     # 消隐比例因子（%）
if M < 20:
    h_blank = 2 × 8 × floor(20 × h_active / 80 / 16)      # 强制 20% 档
else:
    h_blank = 2 × 8 × floor(h_active × M / (100 − M) / 16)

h_total = h_active + h_blank
h_sync  = floor(0.08 × h_total / 8) × 8         # 行同步固定占 h_total 的 8%，量化到 8
h_back  = h_blank / 2
h_front = h_blank − h_sync − h_back

pixel_clock (MHz) = 0.25 × floor(h_total / H_PERIOD_EST / 0.25)
```

例：`1920×1080@60` → `h_total 2576`、`v_total 1120`、`pixel_clock 173.00 MHz`、`h_blank 656`。

### 3.3 简化消隐（`cvt_rb`）与 `cvt_rb2`

两条路径共用同一套骨架，只有 5 个常量不同：

```text
H_PERIOD_EST (µs) = (1e6 / refreshRate − 460) / v_active

V_SYNC_BP = max( floor(460 / H_PERIOD_EST) + 1,  K_MIN )
v_total   = V_SYNC_BP + v_active
h_total   = H_BLANK + h_active
pixel_clock (MHz) = Q × floor(h_total × v_total × refreshRate / 1e6 / Q)
```

| 变量 | `cvt_rb` | `cvt_rb2` |
| --- | ---: | ---: |
| `H_BLANK` | 160 | 80 |
| `K_MIN`（`V_SYNC_BP` 下限） | `3 + V_SYNC + 6` | `1 + 8 + 6 = 15` |
| `Q`（像素时钟量化） | 0.25 | 0.001 |
| `h_sync` / `h_front` / `h_back` | 32 / 48 / 80 | 32 / 8 / 40 |
| `v_sync` | 按宽高比 | 8 |
| `v_front` / `v_back` | 3 / `V_SYNC_BP − 3 − V_SYNC` | `V_SYNC_BP − 8 − 6` / 6 |

例：`1920×1080@60` → `cvt_rb` 用 `138.50 MHz`（`h_total 2080` / `v_total 1111`）；
`cvt_rb2` 用 `133.32 MHz`（`h_total 2000` / `v_total 1111`）。

### 3.4 查表：DMT

```text
命中条件（三个都必须满足）：
    row.h_active == width
    row.v_active == height
    row.v_freq.toFixed() == refreshRate.toFixed()      # ★ 0 位小数，即 ±0.5 Hz 窗口
    row.interlaced == false                            # ★ 恒为 false，见 §6.3

未命中 → 抛 "no DMT timing found for {W}x{H}@{R}Hz"

命中后按 row.type 分派：
    "non-cvt"  → 直接采用表里的 pix_clock / 各前后肩      # 40 行
    "cvt"      → 用表里的宽高，转 §3.2 公式重算           # 21 行
    "cvt-rb"   → 用表里的宽高，转 §3.3 公式重算           # 25 行
    "CEA-861"  → 转 §3.5 的 CEA 查表                     # 2 行
```

> 表里带 `non-cvt` 的行才用得上真实 `pix_clock`；`cvt` / `cvt-rb` 行只提供"这个分辨率组合是标准的"，
> 具体时序仍由公式重算。

### 3.5 查表：CEA-861

```text
命中条件：
    row.h_active == width
    row.v_active == height
    row.v_freq.toFixed() == refreshRate.toFixed()      # 同样 ±0.5 Hz 窗口
    row.scan == "Prog"                                 # ★ 只能匹配逐行，见 §6.3

命中 → 直接采用表里的 pix_clock / h_total / v_total / 前后肩 / VIC
未命中 → 抛 "no CEA timing found for {W}x{H}@{R}Hz"
```

`CEA` 表含 VIC 1–219 共 154 行，其中 **21 行是隔行（`Int`），算法永远匹配不到**。

### 3.6 时序输出结构（`T`）

```text
pclock (= pixelClock), hactive, hblank, htotal,
vactive, vblank, vtotal,
hfreq  = pclock / htotal,
vfreq  = pclock / (htotal × vtotal),          # 实际刷新率
vfreq_round100, hperiod = 1/hfreq, vperiod = 1/vfreq,
peak_bw      = pclock × colorDepth × factor,
peak_bw_dsc  = 8 × pclock,
line_bw      = peak_bw × hactive / htotal,
active_bw    = vfreq × colorDepth × hactive × vactive × factor,
vblank_duration = vblank × hperiod,
hsync, hfront, hback, hpol, vsync, vfront, vback, vpol,
interlaced, aspect_ratio, field_rate, frame_rate,
dmt_id, dmt_2byte_code, dmt_3byte_code, vic
```

## 4. 带宽公式（核心 4 行）

```js
peak_bw   = pixelClock × colorDepth × factor          // Bandwidth，含消隐
line_bw   = peak_bw × h_active / h_total              // Line
active_bw = vfreq × colorDepth × h_active × v_active × factor   // Active，不含消隐
dsc_bw    = 8 × pixelClock                            // DSC 理论下限
```

要点：

- `colorDepth` 是**每通道**位数，`factor` 是每像素样本数，两者相乘才是每像素位数。
- `line_bw / peak_bw == h_active / h_total`，即行内有效像素占比。
- `active_bw / peak_bw` 等于"有效像素 × 有效行 / 总像素 × 总行"。
- `dsc_bw` 把 DSC 压缩后的目标码率固定按 **8 bpp** 估，与输入的 `colorDepth` 无关。

默认例（`3840×2160@144` / 8 bit / RGB 4:4:4 / `cvt_rb2`）：

| 量 | 值 |
| --- | ---: |
| 像素时钟 | 1306.206 MHz |
| `h_total` / `v_total` | 3920 / 2314 |
| Bandwidth（峰值） | **31.35 Gbps** |
| Active | **28.67 Gbps** |
| DSC | **10.45 Gbps** |
| Line | **30.71 Gbps** |

### 5.4 判定算法

```text
verdict(iface, signal):
    if signal 不存在:                                   → 不支持, reason = "N/A"
    if colorFormat ∉ iface.format:                      → 不支持, reason = "color format <name> not supported"
    if iface.maxColorDepth < colorDepth:                → 不支持, reason = "color depth <n> not supported"

    modes = iface.modes                                   # 已按带宽降序排列
    chosen = null;  bpp = -1
    for m in modes:
        if signal.maximum > m.bandwidth:                  # 这一档扛不住
            if !iface.dsc:            continue
            if chosen && bpp == -1:   continue            # 已选中"无需 DSC"的高档，不再降级
            if signal.dsc > m.bandwidth: continue         # 连最低 DSC 档位都不够，跳过
            a = round(m.bandwidth / signal.clock × 4) / 4 # 该档可提供的 bpp，量化到 0.25
            if bpp == -1 || a > bpp:  chosen = m; bpp = a
            continue
        chosen = m; bpp = -1                              # 带宽够，直接选它
    if chosen == null:                                  → 不支持, reason = "not enough bandwidth"
    → 支持, mode = chosen, dscBPP = bpp
```

要点：

- `modes` 降序，所以**选中的永远是"扛得住的最高档"**；后续更低档会被 `chosen && bpp == -1` 挡住，不会降级。
- DSC 分支只有在"从没选到够用档位"时才会被求值，且取**可用 bpp 最大**的那一档。
- 判定是有序的：**先格式 → 再色深 → 最后带宽**。格式不合格时根本不会去看带宽。

### 5.5 DSC 分档

```text
dscBPP 是"该链路能给到多少 bpp"：

    dscBPP ≤ 0    → 绿色    Supported
    dscBPP ≥ 24   → 浅绿    Supported, requires light DSC compression
    0 < dscBPP < 24 → 琥珀  Supported, requires heavy DSC compression
    不支持         → 红色    Not supported
```

`dscBPP ≥ 24` 表示可用 bpp 已经很高（≥ 24 bit 才需要"轻度"压缩）；越低压缩越狠。
tooltip 里还会附 `Usage = maximum / mode.bandwidth × 100%` 和 `Require = maximum`。

例（默认 `3840×2160@144` 8 bit，`maximum = 31.35 Gbps`）：

| 版本 | 选中模式 | 模式带宽 | dscBPP | 结论 |
| --- | --- | ---: | ---: | --- |
| DP 2.1 | UHBR10 | 38.788 | — | Supported |
| DP 1.4 | HBR3 | 25.920 | 19.75 | Supported, requires heavy DSC |
| DP 1.3 / 1.2 / 1.0-1.1a | — | — | — | Not supported |
| USB-C Alt 2.0 | UHBR20 | 38.788 | — | Supported |
| USB-C Alt 1.0 | HBR3 | 12.960 | 10.00 | Supported, requires heavy DSC |
| HDMI 2.1 | FRL5 | 35.556 | — | Supported |
| HDMI 2.0 / 1.4 / 1.3 | — | — | — | Not supported |

## 6. 逻辑上被禁止的操作

这是本文档最实用的部分：**哪些操作会被拒绝、以什么形式拒绝、哪些是"没设防"的坑。**

### 6.1 硬拒绝（抛异常）

| 条件 | 错误信息 | 检查点 |
| --- | --- | --- |
| 输入不是 `number` 类型，或为 `NaN` | `{name} must be a number` | `guardNumber` |
| 输入等于 `0` | `{name} must be greater than 0` | `guardNumber` |
| 中间量不是有限数（`Infinity` / `NaN`） | `timing calculation produced no valid {字段}` | `guardFinite` |
| `timing = dmt` 且表中无精确匹配 | `no DMT timing found for {W}x{H}@{R}Hz` | 查表结束 |
| `timing = cea` 且表中无精确匹配 | `no CEA timing found for {W}x{H}@{R}Hz` | 查表结束 |
| DMT 命中的行类型为 `CEA-861`，但 CEA 表也无匹配 | `no CEA timing found for {W}x{H}@{R}Hz` | 类型分派 |

`guardFinite` 会检查的字段共 6 个：`pixel clock`、`hactive`、`htotal`、`vactive`、`vtotal`、`vblank`。

**注意**：`guardNumber` 的名字是 `width` / `height` / `refreshRate` / `colorDepth`，
错误信息里的名字就是**唯一**的错误线索。

### 6.2 静默判为"不支持"（不抛异常，但结果无效）

按 §5.4 的顺序：

| # | 条件 | 页面表现 |
| ---: | --- | --- |
| 1 | 色度格式不在该接口允许列表内 | 红色 Not supported，tooltip 给出 `color format … not supported` |
| 2 | `colorDepth > iface.maxColorDepth` | 红色 Not supported，tooltip 给出 `color depth … not supported` |
| 3 | 所有模式带宽都不够，且接口不支持 DSC | 红色 Not supported，`not enough bandwidth` |
| 4 | 接口支持 DSC，但最低档位（8 bpp）仍 > 最高模式带宽 | 同上，仍是 `not enough bandwidth` |

**被能力表明确禁止的组合**：

- **YUV 4:2:0 在这些版本上一律不支持**：DP 1.2、DP 1.0-1.1a、HDMI 1.4、HDMI 1.3、HDMI 1.0-1.2。
- **色深上限 12**：HDMI 1.0-1.2（14 / 16 bit 直接判不支持）。
- **DP 1.3 及更早**：不支持 DSC，所以任何超过 HBR3（25.92 Gbps）的规格直接判死。

### 6.3 结构性无法表达（算法不建模，输入无入口）

以下操作**在这套算法里没有对应的输入参数**，因此逻辑上不可能被表达：

| # | 无法表达的东西 | 原因 |
| ---: | --- | --- |
| 1 | **隔行扫描** | `interlaced` 参数被硬编码为 `false`，所有 `scan == "Int"` / `interlaced == true` 分支都不可达。CEA 表里的 21 行隔行模式、DMT 表里的 1 行隔行模式**永远匹配不上** |
| 2 | **1000/1001 精确时基** | 1000/1001 因子被硬编码为 `1`，59.94 / 119.88 / 23.98 这类时基只能通过"±0.5 Hz 取整"撞上 60 / 120 / 24 的行 |
| 3 | **自定义 blanks / 自定义时序** | 只能从 5 种 `timing` 里选，不能手填 `h_total` / `v_total` / `pixel_clock` / 前后肩 |
| 4 | **CVT 的边框（1.8% borders）** | 相关开关硬编码为"关"，恒定按无边框计算 |
| 5 | **双链路 / 多流 / 拼接** | MST、DSC 切片数（slices）、双 HBR3 拼屏、dual-link 都不在模型内 |
| 6 | **HDR 元数据开销** | `hdr` 标志只用于 tooltip 文案，不进入任何带宽计算 |
| 7 | **音频 / 辅助通道 / 数据通道占用** | 只算视频流，音频和 USB 数据带来的额外开销不计（USB-C 2 lane 是唯一被"预留"的项） |
| 8 | **DSC 的真实约束** | 只做"8 bpp 是下限、bpp 越高越轻"的近似，不校验 DSC 版本、切片宽度、每切片最大 bpp |
| 9 | **物理层现实** | 链路训练失败、EDID 不支持、线缆质量、驱动限制全部不建模 |

> 第 1 条特别容易踩：页面在 UI 上压根没有"隔行"选项，但 CEA 表里 154 行有 21 行是隔行的——
> 也就是说"表里有数据，算法用不到"。

### 6.4 未设防（语义非法，但会被照算）

这些输入在**逻辑上非法**，但校验层不会拦，结果是一串看似正常的数字：

| # | 输入 | 实际行为 |
| ---: | --- | --- |
| 1 | **负数**：`width = -1920` | 只拦 `0`，不拦负号 → `peak = -2.944 Gbps`、`pixel_clock = -122.66 MHz` 照常返回 |
| 2 | **负数刷新率 / 负色深** | 同上，`refreshRate = -60` → `-3.154 Gbps` |
| 3 | **小数分辨率**：`1920.4` | 静默向下取整到 8 的倍数（→ `1920`），不报错也不提示 |
| 4 | **宽度 < 8 px**：`width = 1` | 量化后 `h_active = 0` → 返回 `h_total = 80`、`5.332 MHz` 的荒谬值 |
| 5 | **超大值**：`width = height = 1e9` | 无溢出保护 → 返回 `1.48e12 Gbps` |
| 6 | **任意超高刷新率**：`refreshRate = 1000000` | 照算 |
| 7 | **色深超出所有接口上限**：`colorDepth = 64` | 主带宽数字照算（`25.6 Gbps`），只是所有接口都判不支持 |
| 8 | **`factor` 为 0** | 会算出 `0 Gbps`（UI 上不可达，属于内部常量） |
| 9 | **刷新率 ±0.5 Hz 被吞** | 查表用 `toFixed()`（0 位小数）比较，`59.5` / `59.94` / `60.49` **全部命中 60 Hz 行**；`59.4` 则落空 → `dmt` 直接抛异常 |
| 10 | **CVT 路径宽度向下取整** | `1366×768` 走 `cvt` / `cvt_rb` / `cvt_rb2` 时实际按 **1360** 计算（`h_total 1440`、`68.256 MHz`），但走 `dmt` 查表时是 1366 |
| 11 | **重复行的"后到者胜"** | CEA 表里同一 `(分辨率, 取整刷新率)` 有多行时循环**不 break**，后面的行覆盖前面的：`1920×1080@60` 实际命中 **VIC 76** 而不是 VIC 16；`3840×2160@60` 命中 VIC 107 而不是 97；`3840×2160@120` 命中 VIC 120 而不是 118 |
| 12 | **`aspect_ratio` 只在公式路径有值** | 走 `dmt` / `cea` 查表时该字段为 `undefined`（宽高比反查只在 CVT 生成器里做） |

### 6.5 全局兜底：错误对用户不可见

整个计算包在 `useMemo` 的 `try / catch` 里，**任何异常都被吞掉**：

```text
try:
    result = compute(...)
catch:
    return undefined          # 不记录、不提示、不区分原因

result == undefined  →  Bandwidth / Active / DSC / Line 全部显示 "N/A"
                        所有接口显示 "Not supported"，reason = "N/A"
```

后果：

- 用户看到 `N/A` 时，**无法区分**是"分辨率不标准"、"刷新率差了 0.1 Hz"还是"输入了 0"。
- 移植这套算法时，**必须把这一层改成显式错误提示**（例如"144 Hz 不在 DMT 表中，请改用 CVT-RBv2"），
  否则等于把 6.1 里所有有价值的诊断信息丢掉。

## 8. 常见的坑

- **查表类 timing 只对"标准分辨率"有效**：`3840×2160@60` 在 DMT 里**不存在**（DMT 最大是 4096×2160），
  用 `dmt` 会直接抛异常；CEA 里则有（VIC 107）。
- **刷新率不要写错一位**：`144` 在 DMT 里没有，`143.5` 更没有；差 0.5 Hz 就会从"命中"变"落空"。
- **CVT 路径会改宽度**：非 8 倍数的宽度（1366、2560×1440 的 2560 是 8 的倍数所以没事，1366 不是）会被向下取整。
- **`cvt_rb2` 不带隔行**：`V_SYNC` 固定 8、`v_back` 固定 6，是逐行专用参数。
- **`dsc` 那个数字不是"压缩后的实际码率"**，而是 8 bpp 的理论下限；页面自己也在脚注里说明
  高压缩比下画质可能"非常糟糕"。
- **接口判定不保证能点亮**：它只说带宽够，不说 EDID 里有这个模式。
- **别把 `N/A` 当成"不支持"**：`N/A` 是"算都没算出来"（输入或时序有问题），
  和"算出来了但带宽不够"是两回事。
