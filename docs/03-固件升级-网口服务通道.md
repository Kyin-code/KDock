# 功能说明：KDock 自有 OTA —— 网口升级与服务通道协议（SVC1 / SVR1）

> 相关代码：`src-tauri/src/upgrade.rs`（`Svc::transact` / `SVC_*` 常量 / `crc8` / `net_upgrade_conn`）

## 1. 是什么

设备上有一条 **KDock/Kyin 内部服务通道**：上位机通过 TCP 连到设备（默认端口 `6666`），用一套自定义
二进制帧去**列目录、读写文件、算 CRC、打升级标记、复位**。

> 这条链路依赖设备端实现 SVC1/SVR1；它不是 STM32/ESP 厂商 ROM Bootloader，
> 也不能直接用于一块没有 KDock 服务固件的白板。

它的价值在于：**升级不再依赖串口和 YMODEM**，而且传文件是"按偏移写"的，
可以断点续传、可以只补某一段、可以在写完后让设备自己核对 CRC。

典型链路（视产品而定）：`PC --TCP--> 网关板 --SPI--> 主控`。

## 2. 帧格式

每个请求分两层：**外层包头** + **内层帧** + **CRC8**。

### 请求

```
+---------+-----------+----------------------------------------------------+
| "SVC1"  | len(u16BE)| 内层帧（len 字节）                                  |
+---------+-----------+----------------------------------------------------+

内层帧：
  偏移 0   : 1B  flag（当前为 0）
  偏移 1   : 1B  命令码
  偏移 2-3 : u16BE payload 长度（含状态字段，见响应）
  偏移 4-5 : u16BE seq（序号）
  偏移 6.. : payload 本体
  末尾 1B  : CRC8（覆盖内层帧的**全部**字节，含长度与 seq）
```

### 响应

```
+---------+-----------+----------------------------------------------------+
| "SVR1"  | len(u16BE)| 内层帧                                             |
+---------+-----------+----------------------------------------------------+

内层帧：
  偏移 0-1 : flag（0）
  偏移 2-3 : u16BE plen（= 2 + 数据长度）
  偏移 4-5 : u16BE seq（回显请求的 seq）
  偏移 6-7 : i16BE status（0 = OK，负数见错误码表）
  偏移 8.. : 数据
  末尾 1B  : CRC8
```

### 为什么要有 seq

- 设备端按 seq **去重**：同一条命令重发不会被执行两次（重试沿用同一个 seq）；
- 中间的桥偶尔会把**上一条响应**漏下来，靠 seq 对不上就把它丢掉，
  否则会出现"命令 A 拿到命令 B 的结果"这种整体错位一格的问题。代码最多容忍 4 条无关响应。

## 3. 命令码

| 码 | 名称 | 请求 payload | 响应数据 | 说明 |
| ---: | --- | --- | --- | --- |
| 0x01 | PING | 空 | 空 | 探活；升级后靠它判断设备是否回来 |
| 0x02 | LIST | 路径（≤191B） | 文本，每行 `F <size> <name>` / `D <size> <name>` | 列目录 |
| 0x04 | OPEN | `1B mode(0=读,1=写) + 路径` | `u16BE 句柄` | 打开文件拿句柄 |
| 0x05 | WRITE | `句柄 + u32BE 偏移 + 数据` | `u32BE 写入字节数` | 按偏移写 |
| 0x06 | READ | `句柄 + u32BE 偏移 + u16BE 要读长度` | 数据 | 单次上限 1000 字节 |
| 0x07 | CLOSE | `句柄` | 空 | 关闭句柄 |
| 0x08 | CRC | 路径 | `u32BE crc32 + u32BE 长度` | 让设备算文件校验 |
| 0x09 | DELETE | 路径 | 空 | 删文件 |
| 0x0C | OTA_VERIFY | 包路径 | `版本 + payload CRC + 长度` | 让设备校验升级包（含板卡/版本规则） |
| 0x0D | OTA_APPLY | 包路径 | 空 | 写升级请求（下次启动生效） |
| 0x0E | REBOOT | 空 | 空 | 立即复位 |

## 4. 传输参数

| 参数 | 值 | 原因 |
| --- | --- | --- |
| 写块大小 | 512 字节 | 与设备端缓冲匹配 |
| 块间隔 | 6 ms | 给桥/SPI 留处理时间，避免丢帧 |
| 读单次上限 | 1000 字节 | 设备端限制 |
| 读/写超时 | 6 s | 升级期间比平时（50 ms 轮询）宽松，避免误判断线 |

## 5. 网口升级完整流程

1. 连上 `设备IP:6666`（或用工具里已经连好的那条 TCP Client 连接）；
2. `OPEN` 写模式，拿到句柄；按 512 字节+6 ms 把 `.fw` 按偏移写进设备的固件目录；
3. `CLOSE`；再 `CRC` 一次，把设备算出的 `crc32/长度` 和本地 `.fw` 对比 —— 不一致就直接停，
   不会把坏包提交给设备；
4. `OTA_VERIFY`：设备自己再校验一遍包头/板卡/版本规则，返回版本号与 payload CRC；
5. `OTA_APPLY`：写入升级请求；
6. `REBOOT`，然后每 1.5 s `PING` 一次等设备回来：**先看到失败**（桥重建/设备重启），
   之后连续 2 次 `PING` 成功才算"回来了"，总超时 150 s。

## 6. 设备返回的错误码（`status`）

| 值 | 含义 |
| ---: | --- |
| 0 | OK |
| 1 | 参数不对 |
| 2 | 句柄用完 / 文件不存在 |
| -3 | 不是 .fw 升级包 |
| -5 | 包头 CRC 错 |
| -7 | payload CRC 不匹配 |
| -8 | 板卡型号不匹配（拿错包了） |
| -15 | 硬件版本不同，不允许升级 |
| -16 | 版本低于允许的最低版本（禁止降级） |
| -17 | 升级包版本格式太旧（四段式老包） |
| 0x7FFF | 网口桥超时（内部 SPI 没回） |

## 7. 排错

- **一直"响应序列号对不上"**：桥在漏旧响应，通常是设备端有别的进程在同时用这条通道；
- **`0x7FFF` 频繁出现**：内部 SPI 链路忙/异常，先确认设备端服务是否在跑；
- **写一半失败**：重新跑一次即可，按偏移写所以会覆盖，最终 `CRC` 会兜住；
- **升级后设备没回来**：设备可能在跑自检；日志里会看到"设备已回来(用时 N s)"或超时报错。
