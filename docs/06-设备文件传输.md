# 功能说明：设备文件传输（串口 base64 / 网口服务通道）

> 相关代码：`src-tauri/src/upgrade.rs`（`serial_list` / `serial_pull` / `serial_upload` / `svc_pull` / `svc_upload`）、
> `src-tauri/src/lib.rs`（`device_*` 命令）

## 1. 是什么

升级链路的"前半截"：把设备上的文件**取回本机**、把本机的文件**送到设备**，外加列目录、
看大小、算 CRC。设备页的「文件管理」和 Agent 的 `device_*` 工具用的都是这套。

两条通道各有取舍：

| | 串口 | 网口（服务通道） |
| --- | --- | --- |
| 依赖 | 设备 shell（cshell） | 设备上的服务端口 |
| 目录 | 跑 `ls` 解析回显 | `LIST` 命令返回结构化文本 |
| 传输 | `base64` 分块写文件 | 按偏移读写（可续传） |
| 速度 | 受波特率限制 | 快得多 |
| 适用 | 没有网口的设备 | 有网口的设备 |

## 2. 串口通道

设备端 shell 提供两条命令（参数由上位机拼）：

```
ls <dir>                          # 列目录：靠解析回显（"F/D <size> <name>"）
get <file> -t base64              # 把文件按 base64 吐出来
put <file> -t base64 -s <size>    # 接收 base64 数据并落盘
```

上位机的做法：

1. **列目录**：发 `ls <dir>`，按行解析设备回显；
2. **取文件**：发 `get ... -t base64`，边收边把 base64 解码成字节（收到提示符/结束标记为止）；
3. **送文件**：先把内容 base64 编码，再按块发 `put ...`，发完等设备的完成回显；
4. **收尾核对**：必要时再让设备算一次 CRC（见下）和本地对比。

> 为什么用 base64 而不是原始二进制：串口链路上"文本模式"最简单可靠，
> base64 只牺牲 33% 体积，换掉了转义/粘包/流控这一大堆麻烦。
> 大文件（几 MB 的固件）建议走网口通道。

## 3. 网口通道（服务通道）

用 [03 文档](03-固件升级-网口服务通道.md) 里的同一套 SVC1 帧，只是命令换成文件类：

| 步骤 | 命令 | 说明 |
| --- | --- | --- |
| 列目录 | `LIST <path>` | 返回 `F <size> <name>` / `D <size> <name>` 逐行 |
| 打开 | `OPEN <mode> <path>` | mode 0=读、1=写，拿到句柄 |
| 读 | `READ <句柄> <偏移> <长度>` | 单次上限 1000 字节，循环读到 EOF |
| 写 | `WRITE <句柄> <偏移> <数据>` | 512 字节/块，块间 6 ms |
| 关闭 | `CLOSE <句柄>` | — |
| 校验 | `CRC <path>` | 设备算 `crc32 + 长度`，和本地比对 |
| 删除 | `DELETE <path>` | — |

按偏移读写的好处：传输中断可以**接着传**，也能只更新文件的某一段。

## 4. 进度与取消

- 传输过程会持续回调进度（百分比）和日志到界面；
- 点「停止」时，发送循环在下一次检查点退出（不会把当前块切成半块）；
- 已经写进设备的字节**不回滚** —— 重新传一次即可覆盖（按偏移写）。

## 5. 排错

| 现象 | 处理 |
| --- | --- |
| 「设备文件只支持【串口】或【TCP Client(6666)】」 | 当前连接类型不是这两者（比如连的是 UDP），切过去再试 |
| 串口 `get` 卡住 | 波特率太低/文件太大；换网口，或确认设备端 base64 输出没有换行问题 |
| 网口写一半失败 | 看日志里的 status：`2` 句柄用完、`0x7FFF` 桥超时 |
| CRC 不一致 | 传输过程中被截断；重传一次再比 |

## 6. 安全提醒

写文件、删文件都是**直接作用在设备上**的破坏性操作。Agent 侧的这类工具有权限门槛
（「需要批准 / 自动 / 只读」，见 README 的权限说明），手动操作时也请确认目标路径。
